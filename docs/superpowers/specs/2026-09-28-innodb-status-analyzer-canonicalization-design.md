# InnoDB Status Analyzer Canonicalization

## Status

Proposed design approved in conversation on 2026-09-28. Implementation requires review and approval of this document, followed by a written implementation plan.

## Objective

Establish one supported, portable, and testable post-mortem analyzer for `SHOW ENGINE INNODB STATUS` samples while retaining every historical implementation as source material outside the operational path.

The analyzer consumes the hourly sample files generated by `innodb_engine_status.sampler.sh`. It is a read-only analysis tool: it never connects to MySQL and never changes source samples.

## Scope

### In scope

- Promote the current `mysql/innodb/innodb_analyzer/innodb_status_analyzer.v4.sh` behavior as the canonical implementation.
- Publish it at `mysql/innodb/innodb_status_analyzer.sh` without a version suffix.
- Archive all existing analyzer variants under `mysql/innodb/innodb_analyzer/legacy/`.
- Preserve the `v4` analysis semantics, input arguments, report names, and CSV schema.
- Standardize CLI errors, help, TTY colors, non-TTY output, portability, and automated tests.

### Out of scope

- Changing the InnoDB sampler, pt-osc photographer, compression/retention tool, or their output layout.
- Creating wrappers at retired analyzer paths.
- Changing the operational meaning of deadlock, persistent-lock, table, user, or date filters.
- Altering report or recap CSV names used by existing automation.

## File layout and migration

The supported command becomes:

```text
mysql/innodb/innodb_status_analyzer.sh
```

The canonical file is built from the current `innodb_status_analyzer.v4.sh` behavior. The existing root analyzer is a near-identical predecessor and will be preserved, not discarded.

The following files move to `mysql/innodb/innodb_analyzer/legacy/`:

```text
innodb_status_analyzer.root.sh
innodb_status_analyzer.v2.sh
innodb_status_analyzer.v4.sh
innodb_analyzer.multiple.sh
innodb_analyzer_extended.sh
innodb_analyzer_extended.v2.sh
```

`innodb_status_analyzer.root.sh` is the former root-level canonical path. There are no repository references to the retired paths. No compatibility wrappers or symlinks will be created; callers must use the supported root-level command.

## Public CLI contract

```text
innodb_status_analyzer.sh [TARGET] [OPTIONS]
```

Target-selection and existing options remain:

```text
-d, --dir DIRECTORY
-f, --file FILE [FILE...]
-p, --pattern PATTERN
-s, --start 'YYYY-MM-DD [HH[:MM[:SS]]]'
-e, --end   'YYYY-MM-DD [HH[:MM[:SS]]]'
-n, --top NUMBER
-t, --table NAMES
-u, --user NAME
-m, --mode all|deadlocks|locks
-r, --report-mode screen|file|both
-o, --output-dir DIRECTORY
-h, --help
    --no-color
```

Defaults remain `--mode all`, `--top 20`, and `--report-mode file`.

- `--help` exits 0.
- Missing target selection, invalid values, and unknown arguments emit `ERROR:`, print complete help, and exit 2.
- `--no-color` disables styling. ANSI is emitted only to an interactive terminal; redirected output and generated report files are plain text.
- Existing combinations of file-selection options remain accepted and are deduplicated deterministically to preserve the current practical behavior.

## Input and analysis semantics

- Accepted sample filenames strictly match `YYYYMMDD_HH.sample`.
- Invalid filenames are warned about and skipped.
- Date filtering uses timestamps derived from the sample filename and preserves `v4` handling of a missing bound by expanding it to the relevant full day.
- Deadlock extraction, stale-deadlock filtering, persistent-lock aggregation, per-query occurrence counts, table/user filters, output sort order, recap CSV columns, and report naming preserve the `v4` implementation semantics.
- Empty valid input sets and analyses without matching events are successful results with clear plain or colored informational output as appropriate.

## Outputs

The existing `screen`, `file`, and `both` modes remain unchanged in meaning.

- `screen` prints summaries and details to stdout.
- `file` writes the current report and recap CSV artifacts to the requested output directory or current directory.
- `both` does both.

The existing report and CSV filename convention is retained. Reports and CSV files contain no ANSI escape sequences. Source samples are never modified.

## Portability and reliability

The script uses `set -euo pipefail` and explicitly handles expected no-match operations so that an analysis with no events does not abort.

It must run on macOS default Bash 3.2 and common Linux Bash versions. The implementation must not depend on `readarray`, `sort -z`, GNU `sed`, GNU `date`, or `md5sum` alone. It must select a portable hash implementation (`md5sum` where available, `md5` on macOS) while preserving the existing 12-character digest display.

File collection and sorting must retain paths containing spaces and produce deterministic order.

## Test strategy

Add a self-contained Bash fixture suite alongside the canonical analyzer. It will cover:

- Help, color behavior, `--no-color`, required-target and invalid-option failures.
- macOS-compatible execution paths and hash fallback selection.
- Directory, explicit-file, and pattern selection; deduplication; valid/invalid filenames; stable ordering.
- Start/end date filtering and table/user filters.
- `all`, `deadlocks`, and `locks` modes, including no-event success behavior.
- Deadlock and persistent-lock summaries, stale-deadlock exclusion, report mode routing, CSV columns, and ANSI-free artifacts.
- Read-only source-sample behavior.

## Acceptance criteria

1. `mysql/innodb/innodb_status_analyzer.sh` is the only supported unversioned analyzer command.
2. All six historical implementations exist under `mysql/innodb/innodb_analyzer/legacy/`.
3. The canonical analyzer preserves `v4` analytical output semantics and all listed options.
4. The standard CLI/color contract is satisfied in TTY and redirected execution.
5. The analyzer runs on macOS Bash 3.2 and Linux Bash without GNU-only assumptions.
6. The fixture suite, Bash syntax validation, and whitespace validation pass.
